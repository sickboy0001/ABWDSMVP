# エージェントベース経済シミュレーション (ABWDS) 仕様書

## 1. アプリケーション概要

現実の経済・社会構造に近い複雑なシナリオ（格差、税制、インフレ、行動選択など）をシミュレーションし、資産の偏りや生存戦略を分析するためのWebアプリケーション。

## 2. システム環境・技術スタック

* **フロントエンド**: HTMX（フロント）
* **バックエンド / API**: Rust（バックエンド）
* **データベース**: SQLite (Turso)
* **インフラ**: Cloudflare
* **認証機能**: ユーザーログイン機能（セッション管理、シナリオ保存・共有用）

---

## 3. シミュレーション共通仕様・パラメータ設定

各シナリオの要素は、UI上で個別にパラメータを有効化・調整（カスタム登録）できるモジュール構造とする。

### 3.1. 共通の基本フロー

1. **初期化**: 参加人数、初期資産分布を設定してエージェントを生成。
2. **ターン処理**: 毎ターン以下の順序でイベントを処理。
* 行動選択（参加/待機/投資など）
* マッチング（対戦または孤立）
* バトル・賭博処理（勝敗判定、資産移動）
* 再分配イベント（弱者救済、基本所得、累進課税、インフレなど）
* 脱落判定（破産・貧困脱落）


3. **終了判定**: 残存人数が規定に達した際、または最大ターン数に到達で終了。

---

## 4. 機能・モジュール仕様

### 4.1. 基本ルール（公平・不公平な資産）

* **公平な資産**: 全プレイヤーに一律の初期資産（例: 10,000円）を付与。
* **不公平な資産**: 初期資産に格差をつける（例: 9,000円が10%、10,000円が80%、11,000円が10%など、割合と金額を個別に設定可能）。
* **マッチングと対戦**:
* 誰と戦うかは基本的にランダム（コネ社会モードで制限あり）。
* 掛け金は「両者の所有金額のうち、低い方の金額」を基準とする（または資産比例賭博ルールへ移行）。



### 4.2. 行動選択系モジュール

* **挑まない戦略（ゲーム回避）**:
* 一定割合のプレイヤー（例: 20%）が毎ターン戦闘を回避して待機する。


* **投資家型**:
* 毎ターン「参加（ゼロサム戦闘）」か「投資」を選択。
* 投資成功で＋20%、失敗でー20%の変動。


* **学習エージェント（性格・動的変化）**:
* 性格: 保守型 / 積極型 / 超積極型
* 状態遷移: 3連敗で「保守化」、3連勝で「積極化」など、勝敗に応じて動的に行動方針が変化。



### 4.3. バトル・勝敗補正モジュール

* **強者優遇**:
* 資産額に応じた勝率補正（例: 1万円未満は50%、1万円以上は55%、2万円以上は60%、5万円以上は70%）。
* 確率が競合する場合は、双方の勝率を比較して相対調整。


* **資産比例賭博**:
* 低い方の金額ではなく、「各々の資産の〇%（例: 10%）」を取り合う。大金持ちの変動幅を観察。



### 4.4. 再分配・社会制度モジュール

* **弱者救済**: 上位〇%の層から、下位〇%の層へ毎ターン定額（例: 500円）を移譲。
* **累進課税**: 一定資産以上（例: 5万円以上で10%、10万円以上で20%など）のプレイヤーから徴税し、格差抑制効果を検証。
* **基本所得 (UBI)**: 全プレイヤーに毎ターン一定額（例: +500円）を支給。
* **インフレ**: 毎ターン所持金が一定割合（例: -5%）減少。持っているだけでは目減りする構造。

### 4.5. 環境・情報モジュール

* **貧困脱落**: 所持金が一定額（例: 100円未満）を下回ったプレイヤーは強制退場（生存競争のシミュレーション）。
* **コネ社会**: 完全ランダム対戦を廃止し、指定されたグループ内（例: 東京グループ、大阪グループ、名古屋グループなど）でのみマッチング。地域格差の発生を観察。
* **情報格差**: 一部のプレイヤー（例: 上位20%）のみ、対戦相手の正確な資産残高を確認できる。

## 5. 画面・UI構成案

1. **ログイン画面**: ユーザー認証（Turso DB連携）。
2. **ダッシュボード / シナリオ設定画面**:
* プレイヤー数、初期資産、各モジュール（強者優遇、累進課税、BIなど）のON/OFFおよび詳細パラメータの入力フォーム。


3. **シミュレーション実行画面**:
* ターンごとのアニメーション / グラフ描画（資産分布の推移、生存者数など）。
* 1,000〜10,000人規模:画面のメインは HTML5 Canvas または軽量なグラフライブラリを使用する。
* 1万人全員のアイコンを動かすのではなく、ヒストグラムやサンプリング表示に割り切る。
* 重い計算処理はRust（バックエンド）に任せる。
* この規模になると「ゲーム的なリッチなアニメーション」というよりは、「リサーチツール・経済ダッシュボード」のような洗練された見せ方がしっくりきます。


4. **結果・分析画面**:
* 最終的な資産格差（ジニ係数など）、勝敗履歴、ログのエクスポート機能。

### 各コンポーネントの仕様詳細

#### (1) 左サイド: パラメータ設定パネル（HTMX統合）

* **特徴**: 入力値を変更した際、ページ全体をリロードせずにHTMXがRustバックエンドと通信（`hx-post="/api/simulation/preview"`）。シミュレーション実行前であれば即座に初期状態の予測ヒストグラムが再描画されます。
* **アコーディオン形式**:
1. **基本設定**: エージェント数（Slider: 100〜50,000人）、ターン数制限、初期分布（ジップ則、正規分布、カスタム設定）。
2. **行動選択**: 投資家型の割合、学習エージェントの閾値（連勝/連敗での性格遷移ルール）。
3. **再分配・社会制度**: UBI、累進課税ブラケット、弱者救済の送金率。
4. **環境設定**: 脱落ライン（例: 資産100円未満）、コネ社会（グループ数・グループ間移動率）。



#### (2) 中央: リアルタイム視覚化キャンバス

10,000人のシミュレーションを60fpsで滑らかに表現するため、**HTML5 Canvas (2D Context または WebGL)** を採用します。

* **ビュー切替タブ**:
* **タブA：資産階層ヒストグラム（推奨・デフォルト）**
* 横軸を資産帯（対数スケール対応）、縦軸を「人数」としたバーチャート。
* UBI対象領域（赤）、課税対象領域（青）を帯状にハイライト表示。


* **タブB：コネ社会 ネットワークグラフ（サンプリング表示）**
* 全員を表示すると描画コストが高すぎるため、「各地域グループから代表100名ずつ（計数百名）」をサンプリング抽出し、ノードとリンクで対戦・資金移動を可視化。


* **タブC：ローレンツ曲線 (Lorenz Curve)**
* 完全平等線（45度線）と、現在のリアルタイム資産分配率を描く曲線。積算面積からジニ係数を視覚的に表示。




* **再生コントロールバー**:
* 再生/一時停止/1ターンコマ送り/高速化（1x, 5x, 20x, MAX）。
* MAXモード時はCanvas描画をスキップし、Rustバックエンドの計算速度限界（毎秒数千ターン）で回して結果のみを更新。



#### (3) 右サイド: リアルタイム統計・指標パネル

* **主要KPI（ビッグ数字表示）**:
* **ジニ係数 (Gini Index)**: 0.00（完全平等）〜 1.00（完全不平等）。数値の上昇/低下を赤・緑の矢印インジケーターでリアルタイム表示。
* **生存率 (Survival Rate)**: 脱落していないエージェントの割合。


* **資産分配パイチャート**:
* 富裕層（上位1%）、中流層（上位10-50%）、貧困層（下位50%）の所有資産割合。

## 技術実装ハイライト (HTMX × Rust × Canvas)

HTMXとRustの強みを最大化するための画面内データフロー設計です。

```
[フロントエンド (HTMX / JS)]                     [バックエンド (Rust)]
       │                                                 │
       ├── (1) パラメータ変更 (hx-post) ─────────────────►│
       │◄── (2) 設定HTML / 初期状態データ (HTML/JSON) ─────┤
       │                                                 │
       ├── (3) シミュレーション開始 (WebSocket / SSE) ────►│
       │                                                 │ Rustマルチスレッドで
       │◄── (4) 毎ターンの集計データ (バイナリ/JSON) ──────┤ 高速計算 (Rayon等)
       │    (10,000人分の座標ではなく集計配列)            │
       │                                                 │
   [Canvas描画]
   (配列データを受け取り高速描画)

```

1. **データ量の最適化**:
10,000人全員の毎ターンの個別データ（全データ点）をフロントに送ると通信がボトルネックになります。Rust側で「ヒストグラムのビン（例: 100等分した階層データ）」と「主要統計値（ジニ係数、平均値、生存数）」に集約して送信（1ターンあたり数KB以下）します。
2. **リアルタイム通信**:
スタートボタン押下後は、HTMXのPolling（`hx-trigger="every 100ms"`）または WebSocket/SSE (Server-Sent Events) を接続し、Rustから送られる集計ストリームデータでCanvasとChartを更新します。
3. **パラメータ変更の非同期適用 (HTMX)**:
シミュレーション実行中に「途中で基本所得（UBI）をONにする」といった介入操作（Policy Intervention）も、HTMXのボタン（`hx-post="/api/simulation/inject-policy"`）一つでRust側の実行状態フラグを安全かつ即座に書き換えます。

シミュレーションの「再現性（Reproducibility）」と「決定性（Determinism）」を確保するためには、**擬似乱数生成器（PRNG）のシード値管理**と**試行・ターンごとのログ記録構造**を明確に定義することが極めて重要です。

## 3. 再現・再実行（Replay）機能の実現メカニズム

完全な再現性を確保するため、Rustバックエンドでは以下のようにアルゴリズムを組み立てます。

### 1. 決定論的擬似乱数（PRNG）の採用

Rustの標準乱数ではなく、シード固定が保証される軽量・高速な乱数ライブラリ（例: `rand_chacha` や `pcg_rand`）を使用します。

```rust
use rand::SeedableRng;
use rand_chacha::ChaCha8Rng;

// シード値をDBから取得して乱数生成器を初期化
let seed: u64 = run_record.seed; 
let mut rng = ChaCha8Rng::seed_from_u64(seed);

// 以降、マッチングや勝敗判定の確率計算はすべてこの `rng` を使用する
// これにより、同じ seed であれば全く同一の乱数列が発生し、結果が100%完全一致する

```

### 2. 再実行（Replay）の3つのモード

UI上でユーザーが再実行を行う際、目的に応じて以下の3つのリプレイモードを選択できるように設計するのが効果的です。

1. **完全再実行（Exact Replay）**
* **動作:** 保存された `seed` と `config_json` をそのまま使用して再計算します。
* **用途:** 他のユーザーに同じ結果を見せたい場合や、検証用。


2. **同条件・別世界線（New Seed Run）**
* **動作:** `config_json`（ルール）は全く同じで、**新しい `seed`（新しい乱数）** を割り振って実行します。
* **用途:** 「たまたまその結果になった（運）」のか「制度的に必ずそうなる（必然）」のかを複数回試行して検証するため。


3. **パラメータ修正・分岐実行（Fork / What-If Run）**
* **動作:** 既存のシミュレーションの特定のターン（例: Turn 100）時点の状態を再現し、途中からルール（例: 累進課税ON）を変更して分岐実行します。
* **用途:** 政策介入の効果測定。
